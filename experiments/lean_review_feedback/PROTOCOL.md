# LRF-01: native contract and foundation feedback for proof-generating models

Application of the RefutationBench CG-11/12 work and the MathCan review pilot. This is a new post-score development audit of LR-01 and does not modify any registered LR/RAM/FC outcomes or open RAM-18 prospective TEST. No new model fit.

## Feedback contract
The task's original statement, environment, and allowed kernel axiom set are owned by the verifier. The submitted candidate has an explicit statement and structured proof trace. A trusted renderer builds a Lean declaration. A complete proof receives separate native validity, foundation and statement-contract verdicts. Native compilation and #print axioms of the selected declaration establish the first two. A fresh process recompiles the same submitted source followed by a proof of definitional equality of the advertised and expected proposition (rfl), and an explicit application of the selected declaration at the expected type. This deliberately requires the same formal task type, rather than a natural-language judgment. A valid proof of an easier conclusion or a theorem with an extra premise does not receive target reward. Foundation violations also cannot receive reward. Incomplete, malformed, timed-out or infrastructure-failed attempts are not promoted into successful or mathematically false examples. Only completed, independently native-checked exact certificates receive reward 1. Known wrong-contract and excluded-axiom submissions receive reward 0; incomplete/unknown results are censored. An invalid or incomplete proof is not evidence that the proposition is false.

The implementation accepts bounded Horn data and integer action traces, not arbitrary executable model-generated Lean. Synthetic adversarial candidates use fixed renderer templates; unauthorized axioms are scoped to the candidate fixture. Independent source/contract compilation and axiom inventories are archived. No claim of safe execution of arbitrary untrusted Lean or general semantic equivalence.

## Registered pilot
Pinned LR-01 historical source at 3d8243818858c19c5031c36e2bf7e328f831cf25, Lean 4.19.0. Rebuild its frozen corpus and check tasks/source SHA256 against the original manifest. Check the committed compressed prediction receipt's Git blob hash, audit all 384 recorded test traces against the original task, then use the first 32 case IDs in each historical test stratum (64 total, selection fixed before reading outcomes) for native reward replay. Reuse the actual submitted traces and original minimum-step budget; preserve incomplete attempts as censored and do not award retroactive registered score.

On the first 16 historical validation tasks, generate eight matched control submissions per task: correct trace; easier target; added target hypothesis; added direct implication; forbidden proof axiom; forbidden axiom via alias; unused forbidden axiom alongside the correct trace; incomplete trace. Require all 96 complete control submissions' expected outcomes plus the 16 unused-axiom positives (112 complete submissions in total) to match the independent native gate, with the 16 incomplete traces censored. The model receipt and validation control populations stay separate. Record per-axis results, exact accepted axiom sets, compiler calls, wall time, hashes and rejection reasons. Acceptance gate: no false positive reward, no accepted wrong statement, all complete frozen model traces in the 64-case sample receive reward 1, and no incomplete attempt receives a positive label. This is a deployment sanity check, not evidence of learned superiority. A native infrastructure failure blocks release.

## Integration
Use evaluate_candidate(task, candidate, out, lean) from reward.py after a policy proposes a full structured proof. Return a vector of auditable results and a conservative terminal reward. The existing LR-01 exact graph legality mask remains; this is a post-execution guard. For RAM's native tactic gym, retain its pinned exact original-header renderer and independently verified compiler/axiom gates; do not replace them with the Horn adapter. A future separate native tactic adapter should use the same receipt vocabulary and trust boundary, with all historical metrics frozen.
